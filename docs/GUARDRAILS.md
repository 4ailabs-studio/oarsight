# Guardrails

Oarsight gives feedback to clinicians about real conversations with patients. Wrong feedback, invented quotes, or anything that looks like medical advice would do harm, so every stage has guardrails.

**Principle: the model proposes, the code decides.** Language models may label, select, and phrase; deterministic code checks their output against the transcript and the rules before anything reaches the clinician.

Status: ✅ implemented and tested · 🔜 planned (with the day it lands, see the [build log](BUILD_LOG.md)).

Several patterns here (treating input as data, naive-vs-protected comparison, counterfactual pairs, per-agent tool permissions) were inspired by the workshop [JTapiaR/Evalmultiagente](https://github.com/JTapiaR/Evalmultiagente). No code was taken from it; everything in Oarsight is written for this project.

## 1. Scope: communication feedback, never medical advice
| Guardrail | Status |
|---|---|
| Feedback is about how the clinician communicates; Oarsight never diagnoses, assesses the patient's health, or recommends treatments | ✅ stated in README; 🔜 enforced in prompts and UI |
| Clinical topics left open in a consultation are shown only as neutral reminders, never as recommendations | 🔜 Oct 30 |
| Output filter rejects feedback that contains treatment instructions or dosing | 🔜 Oct 30 |

## 2. Data, privacy and consent
| Guardrail | Status |
|---|---|
| Only fictional or role-played consultations in development and demo | ✅ README, data notice |
| Audio, transcripts, profiles and evaluation data stay in `datos/`, excluded from git | ✅ `.gitignore`, checked before every commit |
| API keys only in a local `.env` (owner-only permissions), never committed; GitHub secret scanning and push protection on | ✅ |
| Only Standard-mode models, whose content is not used for training; Contributor-mode models are refused by code | ✅ `llm.py`, test |
| Private mode: the analysis can run on Muse Spark Open (open weights) via Baseten | ✅ `llm.py` (roles); 🔜 every stage |
| Consent screen before recording or uploading | 🔜 Nov 2 (UI) |
| Minimal redaction of personal identifiers (phone numbers, e-mail addresses, Mexican CURP/NSS, dates of birth) in the transcript before any analysis model sees it. Names spoken in free conversation are hard to detect reliably and are **not** covered; the audio itself is still sent to the speech model | 🔜 Oct 28 |

## 3. Transcription fidelity
In early tests, a language model asked to transcribe invented a sentence the clinician never said, and another service silently dropped most of a consultation.
| Guardrail | Status |
|---|---|
| Transcript text comes only from the speech-recognition model (Muse Voice Transcribe); no later stage can rewrite it | ✅ `transcription.py` |
| Coverage check: refuses to analyze a session if less than 80 % of detected speech is transcribed or a gap exceeds 20 s | ✅ `coverage.py`, tests |
| Chunks for long audio overlap and are merged without duplicating turns | ✅ tests |
| Vocabulary biasing is off by default (it replaced "insulina" with "metformina" in a test) | ✅ |

## 4. Speakers and utterances
| Guardrail | Status |
|---|---|
| Every speaker role must be justified by literal quotes, which code verifies | ✅ `roles.py`, tests |
| Missing clinician or patient, unverified evidence, or low confidence → the clinician must confirm | ✅ |
| Utterances are exact substrings of their turns, so every quote is traceable | ✅ `utterances.py`, test |
| Very long unpunctuated utterances are flagged for review | ✅ |
| The transcript is data, not instructions: it is passed inside delimiters and every prompt says to ignore instructions spoken in the consultation (e.g. "ignore your instructions"); a test checks that such a phrase does not change the output | 🔜 Oct 28 |

## 5. Coding
| Guardrail | Status |
|---|---|
| Codes come from a closed set ([codebook](CODEBOOK.md)); anything else is rejected | 🔜 Oct 28 |
| Each code must cite its utterance literally and belong to a speaker with the matching role | 🔜 Oct 28 |
| Counter-examples in the codebook against leniency | ✅ `codebook.py` |
| A skeptic reviewer can only downgrade MI-consistent codes, never upgrade | 🔜 Oct 30 |
| Metrics are computed in code, never by a model | 🔜 Oct 28 |
| Short consultations get no global scores, only moments | 🔜 Oct 28 |
| Accuracy reported honestly against expert annotations, coarse and fine codes separately | 🔜 Oct 29 |
| Counterfactual pairs: the same consultation changing one thing. Changing who the patient is (name, gender) must not change the feedback; changing a clinician's advice into a reflection must change the metrics | 🔜 Oct 29 |
| A naive single-prompt baseline is evaluated on the same cases, to show what the guardrails prevent | 🔜 Oct 29 |
| Evaluation scripts state how many API calls they will make and ask before spending credits | 🔜 Oct 29 |

## 6. Feedback
| Guardrail | Status |
|---|---|
| Key moments are chosen only from candidates generated by code (patient said something significant → clinician's response) | 🔜 Oct 30 |
| Every suggested phrasing is at most 20 words and is re-coded to confirm it is the skill it claims | 🔜 Oct 30 |
| Unverified segments never count toward metrics, strengths, or moments | 🔜 Oct 30 |
| At least one strength; one skill to practice, chosen by code from the metrics | 🔜 Oct 31 |
| Every quote in the next-visit briefing is checked against what the patient actually said | 🔜 Oct 31 |

## 7. Agents with tools
| Guardrail | Status |
|---|---|
| Budget of tool calls and time per run; on overrun, fall back to the fixed pipeline | 🔜 Oct 30–31 |
| The only way to finish is a typed delivery tool; deliveries that break a rule are rejected with the reason | 🔜 Oct 30–31 |
| Every tool call is logged | 🔜 Oct 30–31 |
| Each agent declares the tools it may use; any other tool call is rejected. Tools are read-only; writing to a patient's profile requires the clinician's confirmation | 🔜 Oct 30–31 |

## 8. Simulated patient
| Guardrail | Status |
|---|---|
| Resistance is tracked in code, not by the model, so the patient does not open up for free | 🔜 Nov 1 |
| Resistance does not move on low-confidence codes | 🔜 Nov 1 |
| Every practice attempt gets feedback (practice without feedback did not help in a published trial) | 🔜 Nov 1 |
| The persona is fictional and built only from the session's verified content | 🔜 Nov 1 |
